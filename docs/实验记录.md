## 目前的观察

1. **`task_0001`~`0003` 完全稳定**：6 次跑全部 5 步、全部通过。这三个任务没有"选择空间"（单文件、单个明显 bug、改法唯一）。
2. **`task_0004` 在 7~8 步之间浮动**：方案 A 三次 = 8, 7, 7；方案 B 四次 = 8, 7, 7, 7。差异来自"读几个文件 / 按什么顺序读 / 要不要加防御"。
3. **`temperature=0` 不等于确定性，但大多数时候是确定的**：轮次 6 和 7 的输出**逐字相同**（步数、读取顺序、写入内容全一样）；轮次 1 和 5 也一致。说明它**偶尔**换一条路（第 3 步读 engine 还是 stats），不是每次都随机。
4. **两种消息组织方式的分布几乎一样**：方案 A 三次 = 8, 7, 7；方案 B 四次 = 8, 7, 7, 7；`0001`~`0003` 两边全是 5 步。**在这个样本量下观察不到系统性差异**——说明改 harness 消除不了抖动，只能靠重复测量。因此按"没差异就选简单的"原则，选方案 A。
5. **同一个任务存在多种正确修复**：`task_0003` 见过三种写法（`if not numbers: return 0` / `return 0.0` / `numbers = list(numbers)` 再判断），`task_0004` 见过两种（带/不带空列表防御）。以后归因**不能假设改法唯一**，否则会把正确的替换算成"改错"。
