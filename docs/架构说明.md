# 架构说明：为什么切成这些文件

写给"没有架构设计经验"的人。不讲模式名词，只讲**切分的依据**。

---

## 0. 先纠正三处最容易错的理解

### ① pytest 不告诉你在哪一步错的

pytest 只回答一个问题：**现在有几条失败**。它是一个体温计，不是病历。

"错在第几步"是另一个问题，需要三样东西：

1. 每一轮写完文件，**立刻**跑一次测试（不跑就没有中间状态）
2. 把这一次的状态记在**这一步**上（记在运行末尾就没用了）
3. 相邻两步的状态相比（通过→失败，就是翻点）

做这三件事的是 `agent/loop.py` + `judge/runner.py`，**不是 pytest**。
pytest 只是被调用的一方。

### ② 归因 ≠ 闸门

这两件事经常被说成一件事，但它们是两个东西、两个输入、两个输出：

| | 归因 `attrib/` | 闸门 `gate`（在 `cli.py` 里） |
|---|---|---|
| 输入 | **一条** trace | **两批**运行记录（基线版本 + 新版本） |
| 输出 | 哪一轮 + 哪一类 + 证据 | 放行 / 拦下 + exit code |
| 回答 | 这次为什么坏 | 这次改动能不能合 |
| 依赖对方吗 | 不依赖 | **不依赖**。闸门只比 status，不知道原因也能跑 |

归因是给闸门提供**解释**的，不是闸门的零件。闸门先能跑，归因后补——
这也是为什么路线图里闸门（第 11 步）排在归因（第 8、9 步）后面却更简单。

### ③ L1 / L2 / L3 是**任务难度**，不是**失败类别**

你说"错误有三种层级：L1 单函数、L2 跨文件、L3 关系重构"。
这是**题目**的难度，不是**agent 犯的错**的类别。两者一混，`classify.py` 就写歪了。

为什么必须分开：trace 里读不出"这是关系错误"。你能读到的只有——
它改了哪个文件、改了几行、写完是 error 还是 fail、失败用例数变了多少。
"关系错误"是人的判断，不是数据里的字段。

所以：

| 概念 | 存在哪里 | 取值 | 谁用 |
|---|---|---|---|
| 任务难度 | `tasks/*/meta.json` 的 `difficulty` | easy / medium / hard（对应你的 L1/L2/L3） | 分组统计 |
| 失败类别 | `classify.py` 的输出 | 动测试 / 语法崩 / 把绿的弄坏 / 打转 / 只改一半 … | 归因、论文 |
| 归因准确率 | 人工标注 vs 规则输出 | 一致率（kappa） | 论文、简历 |

三者正交。真正有意思的是**交叉表**：L3 任务是不是更容易"打转"？
L1 任务是不是更容易"改了等于没改"？——这张表本身就是论文里的一节。

## 1. 一句话说清整个数据流

```
题库（人写的）
  → 复制一份工作区（agent 只能写这里）
  → 循环：agent 写 → 强制判分 → 记一步
  → trace 文件（一条运行 = 一个文件）
  → 归因：哪一步翻的、哪一类
  → 两版本对比：新坏 / 新修好 / 抖动
  → 闸门：拦不拦
```

**每一层只做一次"形态转换"**。这就是切文件的唯一依据，不是按功能名字切。

---

## 2. 八个层，各自的输入输出

| 层 | 输入 | 输出 | 一句话职责 |
|---|---|---|---|
| `config.py` | 无 | 常量 | 所有魔法数字的唯一来源 |
| `models.py` | 无 | 数据结构 | 层与层之间的合同（合同变了，六处受影响） |
| `judge/runner.py` | 工作区 + 测试 | 一次判分结果（pass/fail/error/none + 用例数） | 裁判 |
| `agent/tools.py` | 路径 + 内容 | 文件读写结果 | agent 的手（且只能在圈内活动） |
| `agent/policy.py` | 对话历史 | 下一个动作 | agent 的脑子（可换：固定脚本 / 真模型） |
| `agent/loop.py` | 任务 + 策略 + 裁判 | 一串 step（每步带状态） | 把"改"和"测"绑成一个回合 |
| `trace/store.py` | 一串 step | jsonl + csv | 落盘 |
| `attrib/*` | 一串 step | 结论（轮次 + 类别 + 证据） | 归因 |
| `judge/diff.py` | 两批记录 | 四分类 | 版本对比 |
| `cli.py` | 命令行 | 打印 + exit code | 把上面串成命令 |
| `report/render.py` | trace + 结论 | HTML | 给人看 |

## 3. 十三个文件，逐个说"为什么它单独存在"

### `config.py`
**为什么单独**：预算和状态字面量会被**所有层**引用。散在各处一定会漂移——
一个人写 `"pass"`、另一个人写 `"PASS"`，统计里就多出一个幽灵类别，
而且你会以为是数据问题，查一晚上。

**依赖**：无。**被依赖**：几乎所有人。

---

### `models.py`
**为什么单独**：它是**合同**。改一个字段，`loop` `store` `attrib` `diff` `cli` `report` 六处都要动。
放一处，你改的时候能一眼看出影响面；散开就没有这个"一眼"。

**第二个理由**：`Step` 和 `RunRecord` 是两种粒度，必须都是 dataclass。
如果用裸 dict，你会在第 40 行写下 `step["test_sate"]`，然后花两小时找这个拼写错误。

**依赖**：无。**被依赖**：所有人。

---

### `judge/runner.py`
**为什么单独**：判分必须是**唯一裁判**。它不能住在 agent 里，否则早晚有人图方便在
工作区里跑测试——那一刻起，agent 就能靠改测试变绿，你所有的归因结论全部作废。

所以物理上（测试目录在 workspace 外）+ 代码上（独立模块）都要隔离。

**它还负责一个被低估的判断**：把"断言失败"和"语法/导入崩"分成两类。
这是两种病：前者是逻辑改错了，后者是一次改动把文件写废了。
混成一类，你的类别分布会把它们画成同一根柱子，然后你永远看不出"它更常犯哪种错"。

**依赖**：`config`、`models`。**被依赖**：`loop`。

---

### `agent/tools.py`
**为什么单独**：它是 agent 唯一的"手"。把手的动作集中在一个模块，
才能在一个地方回答"它能碰到什么"。

关键约束写在这里：所有路径解析后必须仍在工作区内。
这不能写在提示词里——提示词是请求，代码才是约束。

**依赖**：`config`。**被依赖**：`loop`。

---

### `agent/policy.py`
**为什么单独**：把"决定做什么"和"执行并判分"拆开，你才能用**固定脚本**跑通全链路。
没有这一层，你每次调试都要花 API 钱，而且结果不可复现——
同一个 bug 你复现不出来，就永远修不完。

固定脚本是你的"单元测试夹具"，模型是可插拔的实现。

**依赖**：`config`、`models`。**被依赖**：`loop`。

---

### `agent/loop.py`（核心）
**为什么单独**：它是唯一把三件事绑在一起的地方——**动作 → 判分 → 记录**。
这个绑定关系是整个项目成立的前提（没有它就没有"第几步"）。

如果把这段逻辑放进 `cli.py`，你会发现在写第 3 个命令时开始复制粘贴它。

**依赖**：`config`、`models`、`tools`、`policy`、`judge/runner`。**被依赖**：`cli`。

---

### `trace/store.py`
**为什么单独**：需要"读回来"能力的人不止一个——归因要读、报告要读、比对要读。
把序列化写三遍，三份迟早不一致。

它还有一个职责容易被忽略：**cascade 重建**。csv 应该是从 jsonl 推出来的，
不是独立维护的。两份独立维护的数据，一定会有一份是错的。

**依赖**：`config`、`models`。**被依赖**：`attrib`、`diff`、`report`、`cli`。

---

### `attrib/locate.py`
**为什么单独**：它只回答一个问题——**哪一轮**。不要让它同时回答"哪一类"。
两个问题混在一个函数里，你改分类规则时会不小心改坏定位逻辑，而定位错了后面全错。

**依赖**：`models`（只用于类型）。**被依赖**：`classify`。

---

### `attrib/classify.py`
**为什么单独**：它只回答**哪一类**，并且**必须调用 locate 的结果**，不能自己再找一遍。
自己再找一遍 = 两套定位逻辑 = 迟早不一致。

这里也是唯一适合"慢慢长出来"的文件：先 3 类，看了 30 条真实 trace 再加。

**依赖**：`models`、`locate`。**被依赖**：`cli`。

---

### `judge/diff.py`
**为什么和 `runner.py` 分开**：`runner` 判**一个**任务的一次运行；`diff` 判**一批**任务的两个版本。
粒度和输入都不同。放一起，文件名会变成 `judge.py` 然后 500 行。

**依赖**：`config`、`models`。**被依赖**：`cli`。

---

### `cli.py`
**为什么单独**：因为"能跑"和"好用"是两件事。所有逻辑都在库里，
cli 只做三件事：解析参数、调用库、打印结果。

**判断它写得好不好，只有一个标准**：把 cli 整个删掉，库还能被脚本调用。
如果删不掉（说明逻辑漏在 cli 里了），就还没写好。

**依赖**：几乎所有层。**被依赖**：无（它是入口）。

---

### `report/render.py`
**为什么单独**：它是唯一"输出给人看"的层。归因结果对不对是一回事，
别人**信不信**是另一回事——他要在 20 行日志里自己找证据，就不会信。

**依赖**：`models`、`store`、`classify`（拿类别中文名）。**被依赖**：`cli`。

---

## 4. 切文件的四条规则（这套方法可以用在别的项目上）

不要"先想清楚要几个文件然后创建"。那是没经验的写法的反面。

正确顺序：

**第 1 步：用 5 行伪代码把主流程写出来**
```
task → 复制工作区
循环 N 次：{ 决定动作 → 执行 → 判分 → 记一步 }
保存 trace
归因
```
写不出来就先别建文件。

**第 2 步：每个"动词"就是一个模块**
复制工作区 → `judge/runner.prepare`
判分 → `judge/runner.run_tests`
决定动作 → `policy`
记录 → `store`

**第 3 步：每个在模块之间传来传去的"名词"，就是一个 dataclass**
`Step`、`RunRecord`、`Attribution` —— 它们全部住在 `models.py`。
判断标准：**如果两个模块都要构造它，它就属于 models**。

**第 4 步：用两条规则检查**
- **依赖只能单向**：上层 import 下层，下层绝不 import 上层。
  （`runner` 不能 import `loop`，否则你没法单独测判分）
- **两处都要用同一段代码** → 提到公共层（`models` / `config` / 未来的 `utils`）

**反例**：如果按"功能"切，会切出 `utils.py` / `helpers.py` / `common.py`。
这三个名字说明你没想清楚东西的归属，三个月后它们各长到 400 行。

---

## 5. 三条不能破的边界

1. **agent 的手碰不到测试**（`tools.py` 的路径校验 + 测试目录在 workspace 外）
2. **判分只有一个入口**（任何地方判分都调 `runner.run_tests`，不许自己 `subprocess`）
3. **归因不调模型**（`attrib/` 里出现 `import policy` 就是设计坏了）

第三条容易被违反，因为"用模型判一下这步是不是过度拟合"很有诱惑。
但你没法验证它——没有 ground truth，模型说错你也不知道，最后你手上是一个
看起来很聪明、但没法写进论文的东西。
