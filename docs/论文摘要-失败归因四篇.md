# 一、Who&When（这个领域的开创论文）

**英文标题**：Which Agent Causes Task Failures and When? On Automated Failure Attribution of LLM Multi-Agent Systems

**中文译名**：哪个 Agent 导致了任务失败？以及发生在哪一步？—— 论 LLM 多智能体系统的自动化失败归因

**作者**：Shaokun Zhang, Ming Yin, Jieyu Zhang, Jiale Liu, Zhiguang Han, Jingyang Zhang, Beibin Li, Chi Wang, Huazheng Wang, Yiran Chen, Qingyun Wu

**发表**：ICML 2025 **Spotlight**（不是普通 poster）

**代码和数据**：https://github.com/mingyin1/Agents_Failure_Attribution

## 摘要（英文原文）

> Failure attribution in LLM multi-agent systems — identifying the agent and step responsible for task failures — provides crucial clues for systems debugging but remains underexplored and labor-intensive. In this paper, we propose and formulate a new research area: **automated failure attribution** for LLM multi-agent systems. To support this initiative, we introduce the **Who&When dataset**, comprising extensive failure logs from 127 LLM multi-agent systems with fine-grained annotations linking failures to specific agents and decisive error steps. Using the Who&When, we develop and evaluate three automated failure attribution methods, summarizing their corresponding pros and cons. The best method achieves **53.5% accuracy in identifying failure-responsible agents but only 14.2% in pinpointing failure steps**, with some methods performing below random. Even SOTA reasoning models, such as OpenAI o1 and DeepSeek R1, fail to achieve practical usability. These results highlight the task's complexity and the need for further research in this area.

## 中文翻译

> LLM 多智能体系统中的**失败归因**（failure attribution）—— 找出对任务失败负责的 **agent** 和 **step（步骤）** —— 能为系统调试提供关键线索，但目前研究不足、且极其耗费人力。本文提出并形式化了一个新的研究方向：面向 LLM 多智能体系统的**自动化失败归因**。
>
> 为支撑这个方向，我们构建了 **Who&When 数据集**，包含来自 127 个 LLM 多智能体系统的大量失败日志，并带有细粒度标注：把失败关联到**具体的 agent** 和**决定性的错误步骤（decisive error step）**。
>
> 基于 Who&When，我们开发并评估了三种自动化失败归因方法，并总结了各自的优缺点。**最好的方法在识别"哪个 agent 负责"上达到 53.5%，但在精确定位"哪一步出错"上只有 14.2%**，有些方法甚至低于随机猜测。即使是当时最强的推理模型（OpenAI o1、DeepSeek R1），也达不到实用水平。
>
> 这些结果说明这个任务的复杂度，以及该方向需要进一步研究。

## 关键数字

| 指标 | 数值 |
|---|---|
| 数据集规模 | 127 个多智能体系统，184 条失败日志 |
| 数据来源 | GAIA + AssistantBench 的验证集 |
| **Agent-level accuracy（最好方法）** | **53.5%** |
| **Step-level accuracy（最好方法）** | **14.2%** |
| 有些方法的水平 | 低于随机 |

## 对你项目的意义

**这四篇里最重要的一篇。三个原因：**

1. **它定义了这个任务**。你要做"失败归因"，就必须先看它怎么定义输入、输出、评价指标。
2. **14.2% 是你必须知道的基线数字**。如果将来你的方法 step-level 只有 12%，说明没进步；如果到 30%，说明有东西。
3. **它证明了"失败归因"是公认难题**，不是你一个人在挣扎。

**术语**：`decisive error step`（决定性错误步骤）—— 这个词你论文里一定会用到。

# 二、FAMAS（"你的想法"的完整版）

**英文标题**：Who is Introducing the Failure? Automatically Attributing Failures of Multi-Agent Systems via Spectrum Analysis

**中文译名**：谁引入了失败？—— 通过频谱分析自动归因多智能体系统的失败

**作者**：Yu Ge, Linna Xie, Zhong Li, Yu Pei, Tian Zhang（**南京大学** + 香港理工大学）

**发表**：arXiv 2509.13782，2025-09-17

## 摘要（英文原文）

> Large Language Model Powered Multi-Agent Systems (MASs) are increasingly employed to automate complex real-world problems, such as programming and scientific discovery. Despite their promise, MASs are not without their flaws. However, failure attribution in MASs — pinpointing the specific agent actions responsible for failures — remains underexplored and labor-intensive, posing significant challenges for debugging and system improvement.
>
> To bridge this gap, we propose **FAMAS**, the first **spectrum-based** failure attribution approach for MASs, which operates through systematic **trajectory replay** and **abstraction**, followed by **spectrum analysis**. The core idea of FAMAS is to estimate, from variations across repeated MAS executions, the likelihood that each agent action is responsible for the failure. In particular, we propose a novel **suspiciousness formula** tailored to MASs, which integrates two key factor groups, namely the **agent behavior group** and the **action behavior group**, to account for the agent activation patterns and the action activation patterns within the execution trajectories of MASs. Through extensive evaluations against 12 baselines on the Who and When benchmark, FAMAS demonstrates superior performance by outperforming all the methods in comparison.

## 中文翻译

> LLM 驱动的多智能体系统（MAS）越来越多地被用来自动化复杂的现实问题，比如编程和科学发现。尽管前景很好，MAS 并非没有缺陷。但是 MAS 中的**失败归因**——精确定位对失败负责的**具体 agent 动作**——仍然研究不足且耗费人力，给调试和系统改进带来了巨大挑战。
>
> 为填补这个空白，我们提出了 **FAMAS**，这是**第一个基于频谱（spectrum-based）的 MAS 失败归因方法**。它的流程是：系统性地**重放轨迹（trajectory replay）**→**抽象（abstraction）**→**频谱分析（spectrum analysis）**。
>
> FAMAS 的核心思想是：**通过反复执行同一个任务，从多次运行之间的差异中，估计每个 agent 动作对失败负责的可能性。**
>
> 特别地，我们提出了一个为 MAS 定制的**可疑度公式（suspiciousness formula）**，它整合了两组关键因子：**agent 行为组（agent behavior group）** 和 **动作行为组（action behavior group）**，用来刻画执行轨迹中 agent 的激活模式和动作的激活模式。在 Who&When 基准上对 12 个基线的广泛评估中，FAMAS 表现最佳。

## 关键数字

| 指标 | FAMAS | Who&When 最好方法 |
|---|---|---|
| Agent-level | **57.61%** | 53.5% |
| Action-level（step-level） | **29.35%** | 14.2% |
| 对比基线数 | 12 个 | — |
| **replay 次数** | **20 次** | — |
| **单任务耗时** | **约 105 分钟** | — |

## 方法细节（从正文片段）

**两个阶段：**

1. **Trajectory Replay & Abstraction**
   - 把失败的任务重跑 20 次，收集"成功的"和"失败的"轨迹
   - 用 LLM 把混乱的自然语言日志解析成标准化的 **⟨AGENT, ACTION, STATE⟩** 三元组
   - 用层次聚类（hierarchical clustering）合并语义相同的动作（"search for X" 和 "look up X" 视为同一个）

2. **Spectrum Analysis**
   - 借用软件测试的 **SBFL（Spectrum-Based Fault Localization）**
   - 传统 SBFL：在失败测试里执行得多的代码行，更可疑
   - FAMAS：在多次 replay 里**出现频率和失败相关性高**的动作，更可疑
   - 公式：**Kulczynski2 + 频率衰减因子 λ（默认 0.9）**

## 对你项目的意义

**这是你必须正面处理的一篇。原因：**

**你的 `locate` 和 FAMAS 做的是同一件事 —— 找"哪一步该负责"。**

**区别：**

| | FAMAS | 你的 locate |
|---|---|---|
| 信号来源 | 20 次 replay 的动作出现频率 | **单次运行的测试状态翻转** |
| 需要重跑吗 | **需要，20 次** | **不需要** |
| 单任务耗时 | 105 分钟 | 秒级 |
| 能处理多 agent 吗 | 能 | 不能（单 agent） |
| 有对比实验吗 | **有，12 个基线** | **没有** |

**你必须回答的问题**：如果不用 replay 20 次也能接近 29.35%，那你的方法有价值（成本低 100 倍）；如果差很远，那这条路走不通。

**术语**：`spectrum-based fault localization (SBFL)`、`suspiciousness`、`trajectory replay`、`Kulczynski2`。

# 三、LongRCA Bench（他们用的就是你的模型）

**英文标题**：LongRCA Bench: Root-Cause Localization in Long-Horizon Agent Trajectories

**中文译名**：LongRCA 基准：长时序 Agent 轨迹中的根因定位

**作者**：Yunfei Zhang, Boyu Feng, Changhua Pei 等（中科院计算机网络信息中心、阿里通义实验室、清华、新加坡管理大学等）

**发表**：arXiv 2608.15242，2026-08

## 摘要（英文原文）

> In long agent executions, an early error can persist through later actions and checks, while evidence needed to trace its origin is dispersed across the history. Short histories offer limited tests of recovering error origins across substantial subsequent execution. We introduce **LongRCA Bench**: **1,140 complete failed trajectories** from five sources, all human-annotated for responsible roles and earliest decisive root-cause steps. **Reference roots precede completion by a median of 48 recorded steps; 28.4% of trajectories contain over 100 subsequent steps.**
>
> With **DeepSeek-V4-Flash** on the full benchmark, the strongest of five evaluated baselines achieves **13.2% exact root-step accuracy**. We propose **Root-Cause Trajectory Attribution (RCTA)**, a training-free method that organizes original candidate records and explicit handoff instructions for attribution. Segment summaries and a trajectory outline guide candidate retrieval; available handoff records supply upstream instruction context for the final instruction-execution comparison.
>
> With the same backbone and scoring protocol, RCTA reaches **24.1% exact root-step accuracy and 51.1% responsible-role accuracy**. **LongRCA-Mini** provides **200 fixed trajectories** for lower-cost comparative screening. Even with RCTA, fewer than one quarter of reference roots are recovered exactly.

## 中文翻译

> 在长时间的 agent 执行中，一个早期错误可能一直存活到后面的动作和检查里，而追溯它源头所需的证据又散落在整段历史中。**短的历史轨迹不足以检验"在大量后续执行之后还能不能找回错误源头"这件事。**
>
> 我们提出 **LongRCA Bench**：**1,140 条完整的失败轨迹**，来自五个来源，全部由人工标注了**责任角色（responsible role）**和**最早的、决定性的根因步骤（earliest decisive root-cause step）**。
>
> **参考的根因步骤平均比任务结束早 48 步；28.4% 的轨迹中，根因之后还有超过 100 步。**
>
> 在完整基准上，用 **DeepSeek-V4-Flash** 作为骨干模型，**五个基线中最强的一个，精确根因步骤准确率只有 13.2%**。
>
> 我们提出 **RCTA（Root-Cause Trajectory Attribution，根因轨迹归因）**，一个**无需训练（training-free）**的方法。它整理候选记录和显式的交接指令（handoff instructions）来做归因。分段摘要和轨迹大纲用来引导候选检索；已有的交接记录提供上游的指令上下文，用于最后的"指令—执行"对比。
>
> 在相同骨干模型和评分协议下，RCTA 达到 **24.1% 的精确根因步骤准确率**和 **51.1% 的责任角色准确率**。**LongRCA-Mini** 提供 **200 条固定轨迹**，用于低成本的对比筛选。**即使是用 RCTA，也有超过四分之三的参考根因无法被精确找回。**

## 关键数字

| 指标 | 数值 |
|---|---|
| 轨迹数 | **1,140 条**（全部真实失败，**没有注入错误**） |
| 根因到结束的中位距离 | **48 步** |
| 根因后还有 100+ 步的占比 | 28.4% |
| **最强基线（DeepSeek-V4-Flash）** | **13.2% exact root-step** |
| RCTA | 24.1% exact step / 51.1% role |
| **LongRCA-Mini** | **200 条，低成本对比用** |

## 对你项目的意义

**三个直接价值：**

1. **他们用的骨干模型是 DeepSeek-V4-Flash —— 就是你在用的那个。**
   这意味着 **13.2% 是"你这个模型"的基线**，不是别人用 GPT-5 跑出来的。
   **你可以直接对标。**

2. **有 LongRCA-Mini（200 条）**，明确说了是"低成本对比筛选"用的。
   **这是最适合你起步的子集。**

3. **它证明了"长轨迹"才是难点**：根因平均在结束前 **48 步**。而你的任务只有 **5~9 步**。
   **这就是为什么你感觉"太简单"—— 你的轨迹太短了，短到根本不存在"错误传播"这件事。**

**术语**：`root-cause localization`、`long-horizon`、`handoff instruction`、`exact root-step accuracy`。

# 四、Understanding Code Agent Behaviour（解释了你今天的困境）

**英文标题**：Understanding Code Agent Behaviour: An Empirical Study of Success and Failure Trajectories

**中文译名**：理解代码 Agent 的行为：成功与失败轨迹的实证研究

**作者**：Oorja Majgaonkar, Zhiwei Fei, Xiang Li, Federica Sarro, He Ye（UCL + 新加坡）

**发表**：arXiv 2511.00197，2025-10-31

## 摘要（英文原文）

> The increasing deployment of Large Language Model (LLM) agents for complex software engineering tasks has created a need to understand their problem-solving behaviours beyond simple success metrics. While these agents demonstrate impressive capabilities in automated issue resolution, their decision-making processes remain largely opaque.
>
> This paper presents an empirical study of agent trajectories — the execution traces capturing the steps agents take when attempting to resolve software issues. We analyse trajectories from three state-of-the-art code agents (**OpenHands, SWE-agent, and Prometheus**) on the **SWE-Bench** benchmark, examining both successful and failed attempts.
>
> Our investigation reveals several key insights. First, we identify how distinct problem-solving strategies, such as **defensive programming** and **context gathering**, enable success in different scenarios. Second, we find that **failed trajectories are consistently longer and exhibit higher variance** than successful ones, with failure patterns differing significantly between agents.
>
> Third, our fault localisation analysis shows that while **most trajectories correctly identify problematic files (72–81% even in failures)**, success depends more on achieving **approximate** rather than **exact** code modifications.

## 中文翻译

> LLM agent 越来越多地被用于复杂的软件工程任务，这使得我们有必要**超越简单的成功率指标**去理解它们解决问题的行为。虽然这些 agent 在自动修复 issue 上表现亮眼，但它们的决策过程基本上是黑箱。
>
> 本文对 **agent 轨迹（agent trajectories）** 做了实证研究 —— 轨迹就是 agent 尝试解决软件 issue 时留下的执行记录。我们分析了三个最先进的代码 agent（**OpenHands、SWE-agent、Prometheus**）在 **SWE-Bench** 上的轨迹，**成功和失败的都看了**。
>
> 我们的研究有几个关键发现：
>
> 第一，我们识别出不同的解题策略（比如**防御性编程 defensive programming** 和**上下文收集 context gathering**）如何在不同的场景下带来成功。
>
> 第二，**失败的轨迹一致地比成功的更长，而且方差更大**；不同 agent 的失败模式差异显著。
>
> 第三，我们的故障定位分析显示：**大多数轨迹都能正确找到出问题的文件（即使在失败的尝试里也有 72~81%）**，而成功与否更取决于能不能做到**近似（approximate）**的修改，而不是**精确（exact）**的修改。

## 关键数字（从正文片段补充）

| 定位粒度 | 准确率 |
|---|---|
| **找对文件** | **72~81%**（失败的轨迹里也有这个水平） |
| 找对函数 | 约 **27%** |
| 精确匹配人写的 patch（hunk 级） | 约 **5%** |

**其他发现：**
- 失败轨迹比成功轨迹长 **12%~82%**，方差更大 → 被称为 **"doomed trajectory"（注定失败的轨迹）** 特征
- 成功的 run 里，只有 **27%** 的 patch 修改了和人写参考完全相同的函数
- 也就是说：**成功不要求"改得一样"，只要"改得对"**

## 对你项目的意义

**这篇直接解释了你今天一整天撞的墙。**

**你的数据：**

```
QuixBugs 36 条   → 均 5.5 步，全过
boltons 2 条     → 8 / 5 步
requests 3 条    → 7 / 6 / 9 步
```

**这篇论文说：**

> 即使在失败的尝试里，agent 找对文件的概率也有 **72~81%**。
> 瓶颈不在"找"，在"改得够不够精确"。

**翻译成你的情况：**

```
你的任务都是"单点 bug + 有测试 + 模块名直白"
→ 定位 100% 成功（远超 72~81% 的平均水平，因为你的题比 SWE-bench 简单）
→ 改动 1~2 行就够
→ 所以必然全过

不是模型太强，是你的任务没打中"改得精确"这个瓶颈。
```

**还有一句可以用在论文里：**

> "failed trajectories are consistently longer and exhibit higher variance"
>
> **失败轨迹更长、方差更大。**

**这正是你手上 `req_0003` 的特征：9 步（vs 平均 6 步），中间红了 2 次。**

**如果继续跑，你该统计的是"步数分布"，不是"通过率"。**

# 五、四篇合起来说明了什么

## 这个领域的现状

```
Who&When (2025-04)    定义任务，step-level 基线 14.2%
        ↓
FAMAS (2025-09)       SBFL + replay 20 次 → 29.35%，但 105 分钟/任务
        ↓

```

**一年半，从 14.2% 到 24.1%（最好的方法），而且是在"真实长轨迹"这个更难的设定下。**

**这个领域还很早期，天花板远未达到。**

**你有什么：**
- 一套能跑的 harness（6 个工具、步骤级强制判分、轨迹记录）

# 八、补充：LongRCA 正文查证结果（2026-11-04 补）

上面第七节留了一个问题：**他们的轨迹里有没有"步骤级测试状态"？**

**去查了正文，答案如下。**

## ① 轨迹的字段只有四个

论文 Appendix D 原文：

> "Normalization maps each retained execution to an ordered sequence of records covering multi-agent dialogue, planning, tool calls, observations, browser or terminal interactions, and evaluator feedback. Records preserve original content and roles, stable 0-based indices, and available tool and verifier metadata."

Table 14 给出的 `history` 字段：

> "Ordered trajectory records containing **step, name, role, and content**; includes the task instruction"

| 字段 | 含义 |
|---|---|
| `step` | 0-based 步骤编号 |
| `name` | 记录来源（比如 `stay_agent`） |
| `role` | 工作流角色 |
| `content` | 原始内容（纯文本） |

**结论：没有结构化的 `test_state`。**

测试执行的结果**可能**藏在 `content` 里（作为 `terminal interaction` 或 `evaluator feedback`），但**没有"这一步哪几条测试挂了"这种字段**。

## ② 意外发现：轨迹不是 DeepSeek 生成的

摘要里说"With DeepSeek-V4-Flash ... 13.2%"，**那是评测时的骨干模型，不是生成轨迹的模型。**

生成轨迹的是：

| 生成器 | 轨迹数 |
|---|---|
| MiniMax-M2.5 | 681 |
| Kimi-K2.5 | 276 |
| Qwen3.5-Plus | 183 |

## ③ 意外发现：60% 不是代码任务

| 来源 | 数量 | 占比 | 任务域 |
|---|---|---|---|
| SWE-bench Pro | 128 | 11.2% | 软件修复 |
| Terminal Bench 2 | 42 | 3.7% | 终端任务 |
| **TravelPlanner** | **685** | **60.1%** | 旅行规划 |
| VitaBench | 108 | 9.5% | 服务型工具使用 |
| WebArena Verified | 177 | 15.5% | Web 交互 |

**真正和"代码/终端"相关的只有 128 + 42 = 170 条，占 15%。**

## ④ 所以你的 gap 是真的

```
LongRCA 有：轨迹文本（content 里混着日志、工具输出、评审反馈）
LongRCA 没有：结构化的步骤级测试状态（哪几条测试、红还是绿）
你有：每步的 test_state（[] / ['test_a', 'test_b'] / None）
```

**这个信号别人没有。**

## ⑤ 但实验必须自己造数据，不能在他们的数据上做

**原因：他们的轨迹是别人用别的 harness 跑的，你拿不到 test_state。**

**所以你只能：**

```
用你自己的 harness 跑任务
→ 得到"带 test_state 的轨迹"
→ 在这同一批数据上做消融（ablation）：

   输入 A：只给 content 文本           （模拟 FAMAS / LongRCA 的输入）
   输入 B：只给 test_state             （你的方法）
   输入 C：两者都给                    （上界）
   
→ 对比 step-level accuracy
```

**这个设计干净、成本低、有明确贡献。**

**论文里可以这么写：**

> "我们构造了一批同时包含轨迹文本与步骤级测试状态的失败轨迹。
> 在同一批数据上对比两种信号的效果，发现测试状态在 step-level 定位上显著优于纯文本。"

## ⑥ 但有一个必须先解决的问题

**Who&When、FAMAS、LongRCA 全是多智能体（multi-agent）。**

**你的 agent 是单 agent。**

**差别：**

| | 多 agent | 单 agent（你） |
|---|---|---|
| `who`（哪个 agent） | 有意义 | **没意义**（只有一个） |
| `when`（哪一步） | 有意义 | **有意义** |

**所以你的任务定义要收窄成"单 agent 的 step-level 定位"。**

**这不是缺陷**——LongRCA 里 170 条代码/终端轨迹，如果按单 agent 看，role 固定，只剩 step 要定。

**但你论文里必须说清楚这个边界**，不能宣称"解决了通用失败归因"。

## ⑦ 修正后的下一步

```
① 加 bash 工具（半天）
   ↓
② 造 10~15 条终端任务（会失败的）
   ↓
③ 跑，收集带 test_state 的失败轨迹（预计能拿到 5~10 条真失败）
   ↓
④ 消融：文本 vs test_state vs 两者
   ↓
⑤ 如果 test_state 明显更好 → 你有一篇论文
```

**关键假设**：**终端任务上模型会失败。**

**如果加了 bash 它还是全过，那这条路彻底堵死**，那时候只能承认"这个模型在你能构造的所有任务上都不失败"。

**这个假设可以在第 ③ 步用最便宜的方式验证：先跑 5 条，看失败率。**
