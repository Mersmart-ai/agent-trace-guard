## 问题与解决

### 1. 10 步全是 `list_files`（昨天的遗留）

**现象**：4 个任务全 `max_turns`，模型反复调同一个工具。

**排查过程**：

先打印真正发给模型的 messages，确认 history 送到了（送到了）——**所以不是"信息没给"**。

然后用探针做了四组对照：

| 方案 | 结果 |
|---|---|
| A 现有写法 + 思考**开** | 10 步全 `list_files` |
| B 标准 assistant/tool 对话 + 思考开 | `400 reasoning_content` |
| C 现有写法 + 思考**关** | 10 步全 `list_files` |
| **D 标准对话 + 思考关** | **5 步，全过** |

**原因（两个叠加）**：

1. `deepseek-flash` 默认开**思考模式**，API 要求把上一轮的 `reasoning_content` 原样回传；而每轮都是全新对话，带不回去 → 接不上自己
2. history 塞在一条 `user` 消息里，模型把它当"外部资料"，不会认成"我做过的事"

**最终解法（比方案 D 更简单）**：

只在 user 文本里加一句「**以下是你自己刚才已经执行过的动作**」，模型立刻能推进——**不用改协议结构，也不用关思考**。

> 教训：我以为"文字补不了署名，必须改结构"，猜错了。**试一次比推演十次便宜。**

### 2. `temperature=0` 不等于确定性

**现象**：同一个任务、同一份代码，`task_0004` 跑了 5 次，步数是 **8, 7, 7, 7, 7**。

**原因**：服务端有随机性（批处理 / MoE 路由）。第 3 步就分叉（读 `engine.py` 还是 `stats.py`），后面越走越远。

**影响**：跑 1 次得到的数字，无法判断是"常态"还是"运气"。

> **这是项目核心命题的实证**：不做重复测量，会把随机当成性能。

### 3. `test_state` 粒度太粗

**现象**：`"fail"` 只说了"没全过"，看不出"改好一条、改坏一条"。

**解法**：`run_tests` 加 `parse_failed()`，从 pytest 输出里抓 `FAILED ...::test_average`，`test_state` 变成：

```python
None      # 没测
"error"   # 测了但导入失败
[]        # 全过
["test_average"]   # 这条没过
```

### 4. 模型能看到 harness 替它做的判分

**现象**：强制判分的结果存在 `test_state` 里，而 `test_state` 会随 history 一起给模型看 → 它永远不需要主动 `run_tests`，"未验证就提交"这一类就统计不出来。

**解法**：给模型的那份 history **剥掉 `test_state`**（`dict(h)` 复制后 `pop`，不动原对象）。

- 它自己调 `run_tests` → 结果在 `result` 里 → **照样看得到**
- harness 替它测的 → 只在 `test_state` 里 → **看不到**

### 5. `task_0001` 的 `task.md` 描述了一个不存在的 bug

**现象**：`task.md` 写着"加法和乘法算错了"，还给了 `multiply(-1,-2) → 1 # 期望 2`。但 `src` 里 `multiply` 是 `a * b`，`(-1)×(-2) = 2`，**是对的**。

**影响**：模型会去找一个根本没坏的乘法。

**解法**：删掉乘法那段，只留加法。

> 教训：**题目描述和代码会脱节**。造完题必须跑一次，确认"描述的现象和实际输出的现象一致"。

### 6. 7 个任务，全过

**现象**：`task_0001`~`0007` 全部通过，多数是最小步数（5~7 步），几乎不试错。

**连"最隐蔽"的 `task_0007` 也一次过**——它的 bug 是 `median` 漏了偶数分支（`ordered[len//2]`），模型不但补了偶数分支，还顺手加了空列表防御。

**这不是 bug，是结论**：

> 5 类合成 bug、1~3 层调用结构，对这个模型已完全饱和。**自造任务这条路走到头了。**

## 决定

**① 强制判分加在 `agent_loop`，不加在 `write_file` 里。**

`write_file(workspace, path, content)` 不知道 `tests` 在哪；而且工具该只做一件事。

**② 两种消息组织方式（文本 history vs 标准 assistant/tool 对话）等价，选简单的。**

实测：方案 A 三次 `task_0004` = 8,7,7；方案 B 四次 = 8,7,7,7。**分布一样，选代码少的。**

**③ `MAX_TURNS` 10 → 20。**

`task_0004` 需要 8 步，10 步余量太紧。代价："超轮数"这个类别更难触发。

**④ 暂不做强制判分之外的额外约束（如禁止 finish 前不测）。**

理由：目前观察到的 run 里，每次 `write_file` 后模型都会自己 `run_tests`（10/10）。等出现"写多次只测一次"的样本再说。
